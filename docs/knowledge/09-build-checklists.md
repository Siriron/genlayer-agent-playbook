## 9. Build checklists

Two separate checklists now — which one applies depends on which portal track the concept is headed for (see section 10.1). Decide the track before starting, since it changes what "done" means.

### 9.1 Fourteen-point checklist — Projects track (no exceptions)

1. Repo structure: /src, /public, /docs, /contracts, README.md, LICENSE (MIT text, real file), vercel.json, one-sentence GitHub description. No .env, .env.example, or .gitignore — see section 7's confirmed plain-constant chain-config pattern; these files were confirmed unnecessary overhead once the contract address lives as a single hardcoded constant in chains.ts, and dotfiles are invisible in mobile file browsers, which previously made a real regression (a hardcoded address drifting into .env.example) hard to catch. Do not create these files unless a future concept genuinely needs a real secret (an API key, never a public contract address) — that is the one case they'd earn their place back.
2. SVG logo: custom SVG with app name to public/favicon.svg + navbar.
3. Chain config: /src/config/chains.ts — RPC URL, chainId, explorer URL, contract address, as a single plain constant. Never hardcode elsewhere.
4. Chain config sanity check: confirm the contract address in chains.ts is the correct, current deployed address — this is the one place it lives, so this is the one place to check.
5. OG meta tags: og:title, og:description, og:image in index.html. Never a fabricated or unconfirmed URL in og:url — omit the tag entirely if the real production domain isn't known yet, rather than asserting a guess that real link-preview crawlers will scrape as fact.
6. Loading states: skeletons/spinners on every async call. For any write that triggers a nondet/LLM judgment specifically, also show a "this can take several minutes" note under the pending button (see section 7).
7. Error boundary + 404: styled, no blank white crash screens.
8. In-app /docs route: Overview, How It Works, Architecture, Smart Contracts, API Reference, FAQ.
9. README + /docs folder: live URL, contract addresses, TX links, tech stack, setup, architecture. Docs: architecture.md, deployment.md, frontend.md, contracts.md. Include a real LICENSE file and link to it. If the live URL isn't actually deployed yet, say so plainly (e.g. "not yet deployed — run X to deploy") rather than asserting a placeholder URL as if it were real. Use the README structure in `readme-template.md` (Project files) as the starting point — it's built entirely from GitHub's actually-confirmed-safe HTML subset (badges, `<div align="center">`, `<details>`) rather than CSS that GitHub's sanitizer would silently strip; don't improvise raw HTML/CSS styling from scratch.
10. Responsive + clean: mobile/tablet/desktop. No haram. Visual design (colors, typography, layout, theme) is decided fresh for every build with no reference to earlier builds; follow a specific design only when the person specifies one for that exact build. Nothing about a build's look is recorded in this document.
11. **Audit loop — run as its own explicit step, not as a side effect of writing carefully (see section 13.3 for why this is stated this concretely now):**
    - Grep every `.ts`/`.tsx` file's local imports against the real exports of whatever they import from.
    - Grep for hook calls appearing after a conditional at matching or greater indentation within the same function — a proxy for React Rules of Hooks violations. Use a short script, not manual reading alone.
    - Grep every `.ts` (not `.tsx`) file for JSX-like patterns (`return <[A-Za-z]`, etc.) — rename to `.tsx` on any hit.
    - Check brace balance per file as a cheap structural-syntax proxy if a real build/typecheck isn't available in the environment.
    - Sweep for `console.log`, `TODO`/`FIXME`/`XXX`, `localhost`.
    - Check every route/component/breakpoint/loading/error state/link/accessibility concern by hand.
    - Check meta tags and README/docs prose by hand for fabricated or placeholder URLs — these don't always match a literal grep for the word "placeholder."
12. Pre-zip: navbar, footer, all CTAs working, zero console.log/TODO/localhost/placeholders. Also run the pre-handoff verification in section 3 and the complete mandatory nondet audit in section 4 before zipping. Start any new contract from `projects-track-skeleton.py` (Project files) rather than writing the nondet scaffolding from scratch each time — it's the same ten-item-safe structure as section 5's canonical example, but with business logic left as explicit decision points rather than filled in with a specific concept's answers, so it doesn't quietly pull the next concept toward repeating an already-built shape. **Also (Sep 2026, repository-only review): `tests/` must contain direct-mode tests that execute the real contract — start from `direct-mode-test-template.py` — and `pytest tests -q -p no:cacheprovider` plus `genvm-lint check` must both pass before zipping. Run them; a test file that has never been executed is worse than none (SentinelSLA shipped one that errored on its first line). README and docs/deployment.md must say exactly what the tests do and do not prove.**
13. Repo structure handoff: after zipping, provide the full file structure as one-path-per-line plain text AND separate copy-pasteable code blocks, one block per path — or a single zip, if the person's stated preference is a zip (confirm this once per person rather than assuming either format).
14. Novelty check: before building, verify the concept isn't already live/accepted on the portal or in the tracker below.

**Trigger phrase:** "Follow our complete app building workflow" — applies all fourteen points instantly.

**When the user is actively debugging a deployed contract (not building fresh):** prefer GenLayer Studio's own "Run and Debug" panel over redeploying the whole frontend for every test cycle. Only wire up the frontend once the contract itself is confirmed stable. Do not update repo docs (README/docs/*.md/.env) on every intermediate contract fix during active debugging — wait until the user explicitly confirms the contract is done/final, then do one clean, comprehensive documentation pass covering the complete fix history, rather than a partial update after every incremental change. Ask if genuinely unsure whether a fix is the final one.

**If the fix touches storage or settlement logic specifically:** re-run the complete section 4 audit before considering the fix done, exactly as if it were a new contract — a one-branch bugfix is not exempt from the same rigor a full build gets, per section 13.5.

### 9.2 Six-point checklist — Intelligent Contracts track (lightweight, by design)

This track has no frontend and no repo requirement (section 10.1), so most of 9.1 doesn't apply. Do not pad this checklist back up to fourteen points — the whole point of this track is that it's genuinely lighter.

1. **Concept check.** Confirm the concept clears 10.1's "advanced technology" bar and section 2's Test 3 (novelty against the tracker) before writing code. This track's Test 1 is evaluated differently from Projects — re-read 10.1 rather than assuming Projects' adversarial-dispute requirement carries over unchanged.
2. **Full section 3 TIER 1 rules, applied without exception.** Pinned pragma hash, `@allow_storage`/`@dataclass`, `TreeMap` for key-value storage, `json.dumps()` views, integer-only confidence values, `float()` banned from nondet-reachable code — same as every other contract this project builds. Start from `contracts-track-skeleton.py` (Project files), not from `projects-track-skeleton.py` trimmed down — it's built specifically smaller and single-technique-focused from the start, per this track's own scope discipline (see the skeleton's own docstring for why simply deleting fields from the Projects skeleton would still structurally imply the wrong shape).
3. **Full section 4 mandatory pre-deploy audit.** Every contract with a `run_nondet_unsafe` call gets the complete ten-item checklist (including Bug 7's storage-shape check for any nested-dataclass array field, and Bugs 8-10's timestamp/fetch/address-normalization checks), run as literal greps/scripts per section 13.5's confirmed-working process, not eyeballed.
4. **Live-testing in Run and Debug is worth suggesting, once, not enforcing.** Exercising every write method and confirming clean stderr is genuinely the only way to catch a runtime-only failure the static audit can't see (real validator disagreement, actual storage pickling) — Claude mentions this once when handing off a contract on this track, since there's no frontend layer to catch a broken contract before a reviewer sees it, but doesn't treat it as a required step, ask about it repeatedly, or withhold anything pending confirmation it happened. The person decides whether and when to run it.
5. **Submission title and description only** — no README, no docs folder, no LICENSE file, no repo structure. Write the description to make the "advanced technology" case explicit and concrete (name the specific pattern/technique), since a reviewer has nothing else to go on for this track.
6. **Deploy to StudioNet.** This project targets StudioNet exclusively — no dual-network requirement.
