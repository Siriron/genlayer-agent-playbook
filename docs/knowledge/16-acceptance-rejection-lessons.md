## 16. Lessons from eight repos: why each was accepted or rejected (read in full, Sep 2026)

Method: read every contract's design header and core code, ran `genvm-lint check` on all eight, executed pieces of them in direct mode, and read the staff feedback recorded on the portal. Points are as displayed. Observations from a small set, not a scoring formula.

### 16.1 Accepted: what worked, and what could still have been better
- **SentinelSLA (380).** The evidence carries its own timestamps (GHSA `published_at` / `closed_at`), so a time-based claim can actually be judged. Identifier-derived fetch (a GHSA ID, never a URL). Canonical binding done deterministically: repo must exist and echo `full_name`, the advisory's own `source_code_location` must match the registered repo, and ownership needs a file in the repo naming the caller's wallet (a second, independent channel). Consequence is a permanent reputation ledger, no money. A challenge triggers a second independent consensus round. Staff still asked, over two rounds, for canonical binding, duplicate/invalid-filing rejection, an ownership check, and challenge/finalize in the app. *Could have been better:* its test file was never run (0 of 23 tests pass: 7 fail with `ModuleNotFoundError: genlayer`, 16 error with `'VMContext' object has no attribute 'vm'`, run against `genlayer-test` 0.29.2), a nested `gl.nondet` helper fails lint (E010), and HTTP errors are mislabeled. Under the Sep standard the dead test file alone would sink it.
- **RecallGuard (360).** Genuine adversarial pair. Evidence fetched from a government registry by RecallNumber, and the rule-0.8 identity check (does the record's own product fields match the claimed product) is done in plain Python inside the fetch helper, before the model sees the record. Graded 10-tier ladder with a three-gate validator: ordinal tolerance for the slash, exact match for reward-eligibility and for the fabrication flag. Pull-based `withdraw()`. It explicitly fixed a storage-into-nondet gap it found in the reference contract it adapted. Staff's only ask: show the balance and call `withdraw()` in the app, and connect-and-act so the first write does not use stale wallet state. *Could have been better:* no `tests/` folder.
- **MilestoneVault (320).** Five methods. Fixed evidence derived from the locked criterion (GitHub REST API JSON, after HTML scraping failed twice live because the pages are JS-rendered). Binary verdict on purpose, with the reasoning written down. Deadline locked at creation; `reclaim_stake` added after review as a bounded exit; deterministic validation of inputs before they build a fetch URL. A candid gap log. *Could have been better:* no tests; the LLM still reads a number the code could parse.
- **Copyleft (200) and Recourse (200).** Staked two-party disputes. Staff on Copyleft: it does not fetch the disputed files it claims to judge, can leave stakes permanently locked, and lacks filing/cure timeout finalization. Recourse hit a dead end (repeated `unverifiable`) that was fixed. Both carry the `status_code` fetch bug.
- **Common thread:** small and correct scored as high as large (MilestoneVault 5 methods → 320; ProofPulse 15 methods → rejected). What the higher scores share is that the core judgment is bound to evidence that can actually settle it, every locked fund has a bounded exit, and the app completes every flow.

### 16.2 Rejected: root cause, generalized
- **ProofPulse: the evidence cannot answer the question.** It probes an endpoint at *resolution* time to judge an SLA over a *past* window; staff said so. The claimant's logged observations are self-claims, and nothing stops a replayed incident. The docstring itself says it is a deterministic fetch-and-compare with no LLM judgment, so the consensus adds little; the DNS-over-HTTPS "binding" is elaborate and does not fix the timing problem. It also has the `status_code` bug (every real status resolves to `SLA_BREACHED`), one docs file instead of four, and no tests. *Rule:* before building, ask "can this source speak about **when** the claim is about?" If the claim concerns the past, the source must carry historical timestamps (SentinelSLA's does; ProofPulse's cannot).
- **FilingWatch: a recurring obligation that does not recur, and a comparison rule that compares nothing.** `open_check` moves the deadline forward but `period_label` is fixed, so each later checkpoint is judged against the same reporting period and can reuse the original filing. Separately, `_EQUIVALENCE_PRINCIPLE` names `cik_confirmed` and `match_found`, which `_canonicalize` had already removed from the output, and never names `verdict`, the one consequential field. *Rules:* (a) a recurring obligation needs a per-period key derived from a sequence number, evidence whose own period-of-report must equal it, and a test that runs three consecutive cycles; (b) if `prompt_comparative` is used, its principle must name exactly the keys present in the canonical output, verdict first, and a test must assert that; the hand-written validator remains the default; (c) copying a "proven" contract's mechanism inherits its gaps unless you read them.
- **ReturnRecord: the tests tested a copy.** One suite scanned the source text; the other was a hand-written Python model of the state machine. Both said openly that they do not execute consensus, and that honesty did not save it. Live transaction logs cannot be used in a repository-only review. Its first live runs were all voided because the evidence images could not be rendered. *Rules:* import and run the real contract; check the evidence pipeline (here, `render`) end to end before writing lifecycle tests.

### 16.3 Pre-submission red-team checklist (each answer must point to a named test in `tests/`)
1. What exactly is the claim, and can the evidence speak to the time it concerns?
2. Who benefits from a false verdict, and what stops a self-claim, a duplicate filing, or a replay?
3. For every write method: which test reaches it? For every field the validator compares: which test changes only that field?
4. For every verdict value: a parametrized test that reaches it.
5. For every fund path: a test asserting the exact amount and recipient, and a bounded exit (timeout, reclaim, or no-fault settlement) so nothing stays locked forever.
6. Recurring or multi-step flows: a test that runs at least three cycles or every step in order.
7. HTTP 403/404/500 and an unreachable host: each produces the failure marker, never evidence.
8. Any equivalence-principle string: a test that its named fields exist in the canonical output.
9. `genvm-lint check` and `pytest tests` both pass, and were actually run.
10. Every method is reachable from the app; created IDs are returned to the caller, not inferred from a global counter; connect-and-act; the docs list what the tests do not prove.
