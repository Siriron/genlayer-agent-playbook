## 10. Portal submission rules

**Submissions reopened (Aug 2026) on a two-week window, with a new weekly cap and a new second submission track.** This supersedes the "paused ~1-2 weeks" note from July — that pause ended and the portal now runs two parallel weekly quotas:

- **Projects track (existing format, unchanged): up to 2 per week.** Full app — title, description, GitHub URL, live Vercel URL. Everything in this document's sections 1-9 (concept evaluation, contract rules, 14-point checklist) applies in full to every Projects submission. Do not skip any step of the checklist for this track.
- **Intelligent Contracts track (new, lightweight): up to 2 per week.** Contract only — no frontend, no GitHub repo required. Submission needs exactly: the contract itself (advanced/non-trivial GenVM technology — not a toy or a rehash of the WizardOfCoin-tier examples), a submission title, and a description. See 10.1 below for what "advanced enough" means and how this track's own concept discipline differs from Projects.

**Four total submissions per week is the ceiling this creates (2 Projects + 2 Contracts), not a target.** A thin submission on either track to hit the number is the same mistake "depth beats quantity" already warned against — this cap is capacity, not a quota to fill unconditionally.

**Submission description hard limit: under 1000 characters, on both tracks.** Every submission — Projects or Intelligent Contracts — needs a title and a description, and the description must stay under 1000 characters. This is a portal constraint, not a style preference: write the description to lead with the concrete, specific thing being demonstrated (the actual mechanism/technique for Contracts-track; the actual concept + consensus need for Projects-track) rather than scene-setting or narrative framing, since there's no room for both. Count the actual character length before submitting — do not estimate. If a draft description doesn't fit, cut qualifying clauses and secondary detail before cutting the specific technical claim; the specific claim is what a reviewer has to go on, especially on the Intelligent Contracts track where there's no README or repo to fall back on.

### 10.1 Intelligent Contracts track — separate concept discipline from Projects

This track has no frontend and no adversarial-dispute requirement by default — it exists for genuinely advanced, standalone GenVM technology demonstrations, not miniature versions of Projects-track concepts with the UI stripped off.

**Acceptance reality check, stated directly by staff (Discord, builder-announcements, confirmed Aug 2026): this track's acceptance rate has been running around 5%.** Staff called this number a direct reflection of submission quality, not a review-capacity constraint — treat it as a genuine signal that the bar described below is being enforced strictly, not aspirationally. Every concept on this track should be evaluated against that reality, not against the more forgiving "single-technique demonstration" framing alone — a concept passing 10.1's structural tests is necessary but evidently not sufficient at current review standards.

- **Run the Concept Evaluation Framework's Test 1 differently here.** A Projects-track concept without genuine adversarial consensus need fails Test 1 outright (section 2). An Intelligent Contracts submission is not automatically required to have two adversarial parties — a single-party technical demonstration (a novel nondet pattern, a genuinely new evidence-verification technique, a storage pattern nobody's shipped before) is a legitimate use of this track specifically because it's declared as a contract-technology showcase, not a dispute-resolution product. What still applies: the contract must not be the "AI app with GenLayer attached" pattern (section 10's rejection categories) — it needs to demonstrate something that requires GenVM's actual capabilities (multi-validator consensus, real nondet web access, genuine on-chain judgment), not a generic call-an-LLM-once function that happens to be written in GenVM syntax.
- **"Advanced technology" — concretely, not vaguely, and now explicitly reusable, per staff's own stated goal (Discord, Aug 2026): "contracts the community can actually reuse: primitives, patterns, and building blocks that other builders can pick up and integrate into their own projects."** A qualifying contract should show at least one of: a nondet pattern beyond the basic leader/validator template already in section 5 (e.g. multi-source cross-referencing evidence, a genuinely novel settlement/consequence mechanic, chained nondet calls across more than one write function with real interdependency); a storage pattern more sophisticated than a single flat `TreeMap` (e.g. the kind of nested-struct storage question section 4's Bug 7 and section 13 document actually resolving); or integration of a GenVM capability not yet demonstrated anywhere in this project's tracker. Beyond technique novelty alone, the contract should read as something a *different* builder, working on an unrelated concept, could plausibly lift the pattern from — not because it's generic, but because the technique itself (the nondet structure, the storage approach) is cleanly separable from this concept's specific business logic. A contract that's functionally identical to an existing tracker entry with cosmetic changes does not qualify, same as the plagiarism rejection category already states.
- **Two rejection sub-patterns confirmed directly by staff (Discord, Aug 2026), both new, neither previously in this document:**
  1. **A contract extracted from a project already submitted on the Projects track.** Staff's own framing: "that's the same work counted twice." Before submitting any Intelligent Contracts concept, check it isn't the embedded contract from a Projects-track submission (existing or planned) with the frontend stripped off — that's disqualifying regardless of how the contract itself scores against the "advanced technology" bar above. This means a Projects-track build's contract cannot later be repackaged as an Intelligent Contracts submission, and the reverse also doesn't work as a strategy: don't build a contract for this track with a private plan to later wrap a frontend around it for Projects — pick the track once, per concept, and commit.
  2. **A small contract written primarily to learn how consensus works.** Staff explicitly distinguished this from a genuine contribution: "learning is great, and we encourage it, but a learning exercise is not a contribution." This isn't a claim about code quality — a technically clean contract can still read as a learning exercise if its actual purpose, evident from its scope, is exercising the leader/validator pattern rather than demonstrating something new. Concept-check against this explicitly: would this contract exist, in roughly this form, even if the goal were purely to practice the mechanism rather than to contribute a reusable pattern? If yes, it likely reads as a learning exercise regardless of intent.
- **Keep it small.** This track is explicitly for something that doesn't have to be complex to qualify — advanced does not mean large. A single well-executed nondet pattern demonstrating one genuinely new technique is a complete Intelligent Contracts submission. Do not scope-creep a Contracts-track idea into needing a frontend "to really show it off" — if it needs a UI to make its case, it belongs on the Projects track instead, at Projects-track discipline.
- **Section 3, 4, 5, and 6's full rules still apply without exception** — TIER 1 contract rules, the ten-item nondet bug catalog, the canonical pattern, and the debugging methodology are not relaxed for this track. "No frontend/repo required" is about the *submission packaging*, not about contract-writing rigor.
- **Novelty check (section 2 Test 3, section 9.2 checklist item 1) still applies**, checked against the same tracker in section 11 — an Intelligent Contracts submission and a Projects submission both draw from the same "never suggest again" and "already built" lists. A concept doesn't get to reappear on this track just because the packaging is lighter.

**Standing rules (unchanged from before the reopening):**
- No standalone contract *batches* on the Projects track, no documentation-only submissions, no Tools & Infrastructure category — these restrictions are specific to the Projects track and don't apply to the new Intelligent Contracts track, which is itself the sanctioned way to submit a contract without a full Project wrapper.
- Always check the portal for active missions before submitting, on either track.

**Responding to "More Information Needed" (confirmed working, Recourse, Aug 2026) — distinct from an outright rejection.** A rejection (see SourceChecker and Chronomark in section 11) usually needs a structural fix and often shouldn't be resubmitted without one. "More Information Needed" is a different, narrower state: staff have identified something specific and fixable, and the resubmission note itself is what a reviewer reads to decide whether it's actually fixed. Confirmed pattern that worked: state exactly what changed, in concrete terms tied to the original feedback (not "fixed the bug" but the specific mechanism — which function, which condition, what it does differently now); state what proof exists that it's fixed (a specific test, a specific transaction, not just "tested it"); include the updated live evidence (redeployed addresses, updated repo/live links) inline in the same note rather than making the reviewer hunt for them. Recourse's resubmission followed this shape and was accepted at 200 pts — the same score as Copyleft's clean first-pass acceptance, under the same current review standard (see section 10's benchmark discussion; Sigil's higher 320 pts predates the current stricter standard and isn't a meaningful comparison point anymore). This response pattern is confirmed to produce *acceptance* under current review; treat it as the confirmed template for any future "More Information Needed" response.

**New/confirmed rejection categories (apply to both tracks unless noted):**
- AI-app-with-GenLayer-attached. If the core function doesn't genuinely need multi-validator consensus or another real GenVM capability, it shouldn't be a GenLayer contract. (See section 2's Test 1 for Projects; see 10.1 above for how this is evaluated on the Contracts track.)
- Plagiarism. Copying or lightly modifying a previously-rewarded project or contract.
- Format-only validators. Checking that output is valid JSON proves nothing. (Section 3's staff-confirmed validator-rigor rule.)
- Judging from user-submitted text alone. Must fetch real evidence contract-side.
- Live link without source (Projects track only — Contracts track has no live-link requirement by definition).
- Contract double-counted across tracks (Intelligent Contracts track only, confirmed by staff Aug 2026 — see 10.1). A contract extracted from an already-submitted Projects-track build is rejected as the same work counted twice, regardless of how it scores on its own technical merits.
- Documentation that doesn't match the actual build (Projects track, confirmed by staff Aug 2026, Discord). The repo's source and documentation must genuinely match what the submission claims — this is a check on accuracy, not just presence. Section 9.1's checklist already requires docs to exist; this adds that they must be verified against the real, current behavior of the build before submitting, not written once early and left stale as the contract or frontend changes underneath them.
- Generic, non-specific submission notes (Projects track, confirmed by staff Aug 2026, Discord, verbatim: "Generic AI-written intros that don't explain the actual build slow down your review"). Submission notes must describe, in plain terms, what the project actually does, what problem it solves, and how to use it — specific to this build, not a template-shaped paragraph that could describe any GenLayer submission. This is a direct, named risk for a Claude-assisted workflow: a submission description drafted by summarizing the concept in general terms, without naming the actual contract methods, the actual verdict shape, or the actual evidence source, reads exactly like the pattern staff is flagging. Before submitting, check the notes name specific, concrete details from this build (method names, verdict options, evidence sources) rather than describing the concept abstractly.
- Broken or unusable frontend (Projects track, confirmed by staff Aug 2026, Discord, verbatim: "a very messy frontend making the experience impossible can result in a reject"). The frontend "working" in the sense of not crashing is not sufficient — it must genuinely call the contract and handle the full transaction lifecycle (submit, pending, confirmed/error states) in a way a reviewer can actually use to evaluate the concept. This raises the bar on section 9.1 checklist item 6 (loading states) and item 11 (the audit loop) from "present" to "actually usable end to end."
- Tests that do not execute the contract (Projects track, ReturnRecord rejection, Sep 2026): static source scans and a hand-written Python model of the state machine are not tests of the contract. Deployment addresses and transaction logs are inadmissible in a repository-only review. See sections 15-16.
- Evidence that cannot speak to the time the claim is about (ProofPulse rejection, Sep 2026): a live probe at resolution time cannot show what happened during a past incident window. Claimant-logged observations are self-claims. See section 16.
- A recurring obligation whose period never advances, or a comparative-equivalence rule that names fields the canonical output no longer contains (FilingWatch rejection, Sep 2026). See section 16.

**UPDATE (Sep 2026): the 200-pt figure below is a floor, not a ceiling — see section 15 for 320-380 pt acceptances and the tightened review standard.** **Current scoring reality, stated directly by the person running this project (Aug 2026) — supersedes the Sigil/Questera framing below wherever the two conflict.** Sigil's 320 pts (May 31 2026) and the Questera 760pt reference were both set under an earlier, looser review standard. Under current review standards, a Sigil-style submission would be rejected outright — that score is historical fact, not a current target, and should not be used as a calibration point for what a new submission needs to hit. **The calibration set, all reviewed under present standards, is now six submissions: Copyleft (accepted, 200 pts), Recourse (accepted, 200 pts), Chronomark (rejected), DomainClaim (rejected twice), CitationChain (rejected), RetractionWatch (rejected).** Two independent acceptances at 200 pts under strict current review remains the actual signal to build toward — not a gap to Questera's 760, which reflects a bar that no longer applies. The four rejections since Chronomark are informative in a different way than the acceptances: each one names a specific, narrow, fixable defect (see section 11's full entries) rather than a wholesale concept failure — DomainClaim and CitationChain both had genuinely sound overall architecture undone by one precise binding gap each, and RetractionWatch's entire defect was one unreachable enum value. This is worth reading as evidence that the review bar currently rewards narrow correctness on a small number of specific, checkable properties (evidence-identifier binding, verdict-enum reachability, standing/control channels) more than it punishes ambitious scope — a well-executed submission failing on one precise, nameable defect is a different failure mode than a submission failing because the underlying concept was thin, and the fix in the former case is usually small and mechanical rather than a rebuild. Treat 200 pts as a realistic, confirmed-achievable target for a well-executed submission right now, and treat this week's four rejections as evidence for exactly which specific checks close the remaining gap, not as evidence the overall approach needs to change.

**Quality benchmark — working theory of what correlates with acceptance under current standards, given the three-point set above:**
Copyleft and Recourse both passed at 200 pts; Chronomark failed. The genuinely useful comparison now is Copyleft/Recourse's shared traits against Chronomark's actual, confirmed failure (section 11's Chronomark entry: evidence not structurally bound to the named task, no deadline precommitment) — not a gap-to-Questera reading, which no longer reflects the active bar. Working theory, current-standards version:
- Novel narrative — a concept with a genuinely new angle, not a recognizable variant of an existing pattern.
- Working demo depth — a demo that lets a reviewer feel the consensus mechanism doing real work.
- Dual-network deployment was true for the two prior accepted submissions in this project's history at the time they were built, when this project still targeted both StudioNet and Bradbury. This project now targets StudioNet exclusively going forward (section 7) — dual-network is no longer pursued as a benchmark criterion, and its absence in a current submission should not be read as a gap relative to that prior pattern.
- Validator rigor — airtight independent-re-derivation validators on every write (see sections 3-5), including every numeric or categorical field a verdict depends on, not only the coarse verdict bucket itself (section 4's confirmed, generalized rule).
- Evidence structurally derived, never submitter-supplied (section 2's confirmed-twice principle) — this is Chronomark's actual, specific failure, and every accepted build so far satisfies it. Treat this as load-bearing for acceptance, not just aspirational.
- Credible path forward, per staff's own stated expectation (Discord, Aug 2026, verbatim: "Strong projects show a credible path forward: continued development, community adoption, or real external use"). Concretely, this is a claim a submission should be able to substantiate, not just assert: a stated next-iteration plan, an actual (not hypothetical) integration or reuse by something outside this project, or real usage evidence beyond the builder's own testing.

This benchmark is Projects-track-specific (it references demo depth and narrative, which don't apply the same way to a Contracts-track submission) — no equivalent benchmark score is confirmed yet for the Intelligent Contracts track, where the only current data point is Chronomark's rejection. Treat the bullet points above as aspirational for Contracts-track submissions where they're actually applicable (validator rigor applies directly; evidence-structural-derivation applies directly and is Chronomark's own confirmed failure mode; narrative/demo depth don't; credible path forward could apply to a genuinely reusable primitive but isn't stated as a Contracts-track criterion specifically; dual-network no longer applies to either track).
