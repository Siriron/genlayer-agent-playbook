### Copyleft — full entry, reference implementation for evidence-arbitration contracts

**Concept:** On-chain GPL-family license compliance arbitration. Claimant stakes GEN and accuses a downstream repo of violating GPL obligations. Respondent counter-stakes and rebuts. Resolution fetches three independent evidence sources (SPDX canonical license text, downstream repo's own LICENSE/NOTICE file, disputed source path) and runs AI validator consensus to produce a verdict. GPLv3-style cure window lets respondents remediate before stakes are slashed.

### Recourse — full entry, reference implementation for the DynArray-on-nested-dataclass limitation (Bug 7) and for staked deliverable arbitration with a three-way (not binary) verdict

**Concept:** Staked freelance deliverable arbitration. Client locks a specification (discrete, checkable criteria) and stakes payment before a freelancer accepts the engagement — the spec cannot be reshaped by either party after acceptance. Freelancer stakes a smaller good-faith bond and submits a deliverable URL. On dispute, resolution fetches the real deliverable content and judges it against the locked spec, producing one of three verdicts (not two): `compliant`, `non_compliant`, or `unverifiable`. A `non_compliant` verdict opens one cure window for the freelancer; an `unverifiable` verdict opens one refinement window for the client; if evidence still can't establish a verdict after refinement, both stakes return with no penalty to either side.

**Current live addresses (Aug 2026 — supersedes all earlier deployments):**
- StudioNet: 0x5E9460AC23042C959416f2dAF49aa975AB4F1A01
- Bradbury: 0x20719390D0aab6144F9544E63a42215313fD4754
- Frontend: https://recourse-five.vercel.app/

**This is the canonical reference for Bug 7 (section 4) and for a three-way, non-binary verdict design.** Read section 13 in full before touching a nested-dataclass storage field on any future contract — this project's most expensive single debugging cycle since Copyleft was three sequential live failures on exactly this pattern.

**Live-verified, not just theoretically correct:**
- Full `create_engagement` through `accept_engagement`, `dispute_deliverable`, `resolve_dispute`, `refine_dispute`, `resolve_dispute` (again) lifecycle run directly against the deployed contract, reaching `resolved_unresolved`.
- A real portal-review bugfix cycle completed end-to-end: staff feedback (a staff reviewer) identified that a second `unverifiable` verdict after `refine_dispute` had already been used routed back to a state (`unverifiable_pending_refine`) that was then permanently unreachable, locking both stakes with no valid action remaining. Fixed, re-audited against the full section 4 catalog, redeployed to both networks, and re-verified live: the same sequence now correctly reaches `resolved_unresolved`.
- Settlement transfers confirmed via the explorer's Related Transactions view showing exactly two separate `ACCEPTED` transactions fired at the moment of settlement, matching `_settle_unresolved`'s two `emit_transfer` calls — confirmed as two real transactions existing, though the individual `To`/`Value` fields of each were not itemized before this entry was written (a documented, acknowledged residual gap, not an oversight).
- Confidence/rotation behavior on decisive (non-ambiguous) evidence confirmed for the first time on this project — see section 4's updated note under Bug catalog's "additional confirmed characteristics."

**Not yet tested:** the `non_compliant` branch (`submit_cure`, `resolve_cure` reaching `resolved_compliant` or `resolved_noncompliant`) has never been exercised against a live deployment — only the `unverifiable`/refine branch has been proven end-to-end. `cancel_unaccepted` and `accept_deliverable` (no-dispute happy path) are simple and were sanity-checked but not with the same rigor.

**Known, deliberate, unresolved gap:** no deadline/timeout automation — `gl.message_raw["datetime"]`'s actual parseable format was never confirmed against a worked example, so acceptance and cancellation are explicit, user-triggered actions only rather than automatic on a deadline. This is an isolated, low-risk follow-up (a purely deterministic function, never touching the nondet path) whenever the format is confirmed.

**Portal outcome: Accepted, 200 pts (Aug 2026).** Staff response was a generic acknowledgment, not specific technical feedback this time — the resubmission's own content (the fix description, the lifecycle test, the live transaction proof) is what closed the loop, not anything staff added afterward.

**Honest note on the score itself, since it's a real data point worth not smoothing over:** Recourse's 200 pts matches Copyleft's 200 pts exactly, despite very different paths to acceptance — Copyleft was a clean first-pass acceptance, Recourse went through a real staff-feedback "More Information Needed" round and a genuine fix cycle before resubmission. (Sigil's 320 pts is not a meaningful comparison point here — it was scored under a review standard that predates the current stricter one; see section 10's benchmark note.) Two different paths landing at the identical score under current review is itself informative: it suggests 200 pts may reflect something closer to "a solid, correctly-executed submission that clears the current bar" rather than a score that rewards the specific route taken to get there (clean vs. iterated-with-feedback). That's a plausible reading, not a confirmed one — two data points is still thin for a real trend line — but it's a more grounded reading than comparing either score against Sigil's now-stale 320. Going forward: 200 pts is the realistic, twice-confirmed target for a well-executed submission under current standards, whether it arrives via a clean first pass or via a genuine feedback-and-fix cycle; don't assume either path is inherently worth more or less until a fourth data point exists.

**Frontend build note:** two real bugs (a React Rules of Hooks violation, a `.ts` file containing JSX that needed renaming to `.tsx`) were caught only by a deliberate static self-review pass run after the frontend was fully written, not while it was being written. See section 13.3 — this is now a mandatory explicit step, not implied by "write carefully."

**Design principle demonstrated (not previously named as a standing rule):** the spec is locked at `create_engagement`, structurally before the freelancer can accept or any deliverable exists — stated explicitly in the accepted submission's own README as the actual thesis ("the spec itself gets renegotiated after the fact... Recourse removes that by making the spec a locked, on-chain record... before any work begins"). This is the same principle MilestoneVault's criterion-locking independently follows. Now captured as a standing rule in section 4 — was previously implicit in this contract's code without being stated as a reusable pattern.

**Debugging timeline, for reference:** three sequential live storage-construction failures (Bug 7) resolved in one session by escalating to primary SDK source rather than doc prose, followed by a separate real portal-review bugfix cycle (the refine-exhausted dead end) completed and live-verified in a later session. Full retrospective, including what should have caught the storage failures earlier, lives in section 13 — treat that investment as spent and never repeat the same discovery process from scratch on a future contract's nested-array storage question.

### SentinelSLA — full entry, reference implementation for reputation/consequence-based contracts and for the Aug 2026 timestamp/fetch/address-key bug set

**Concept:** On-chain reputation ledger for open-source maintainer security-response accountability. A maintainer locks a repo and a resolution-time commitment on-chain before any advisory exists. When a real GitHub Security Advisory (GHSA) is later published against that repo, anyone can file a compliance check referencing the advisory's own GHSA ID — never a URL, never a free-text claim. The contract fetches the advisory directly from GitHub's own security-advisories API and, if the advisory's own record links one, fetches the actual fix diff (not a rendered HTML page) to judge whether the resolution is backed by a substantive remedy. Verdict (compliant/non_compliant/unverifiable) updates a permanent, public reputation ledger. No stake, no GEN transfer anywhere in the contract — the consequence is standing, not money, making this the first reputation/consequence-shaped concept in this project's tracker with a genuinely complete, live-tested lifecycle.

**Current live address (Aug 2026):**
- StudioNet: 0x9bf02585228D7A7E3d4dcB3a35928045a7C250E8
- Frontend: https://sentinel-sla.vercel.app/

**Live-verified (Aug 2026), not just theoretically correct:**
- `resolve_compliance` tested against three structurally different real GHSA advisories: one still open (GHSA-5j59-xgg2-r9c4, Next.js), one closed with a real, substantive, independently-confirmed fix commit (GHSA-wg6q-6289-32hp, bcgit/bc-java), and one withdrawn as a confirmed false positive (GHSA-x96m-c5fj-q75c, supabase). All three produced the correct verdict branch. Clean five-validator consensus, zero problematic rotations, all three times.
- `resolve_challenge` — the contract's second, fully independent nondet function — tested live once, converged cleanly on the first attempt (`UPHOLD`, matching the correct original verdict).
- Full `register_sla → file_compliance_check → resolve_compliance → open_challenge → resolve_challenge → finalize_compliance → get_reputation` lifecycle run end to end against the deployed contract, with the resulting reputation ledger entry confirmed correctly populated on the first successful attempt after a real bug fix (see below).

**Confirmed empirical finding:** `closed_at` came back null/unset on all three real advisories tested — 3 for 3 live, across genuinely different advisory states (open, closed-with-fix, withdrawn). This should be treated as strong evidence, not merely anecdotal: `unverifiable` is the practical common case for this evidence source, not a rare fallback, and the fix-substantiveness judgment carries more real evidentiary weight in practice than the resolution-hours math does.

**Three real bugs found and fixed through live testing, none of which the seven-item audit that existed at the time (before these three were discovered) could have surfaced beforehand — now section 4's Bugs 8, 9, and 10, folded into the current ten-item audit:**
1. `gl.message_raw["datetime"]` is an ISO-8601 string, not a Unix integer — settles a question this document had left open since Recourse.
2. Plain GitHub commit URLs return HTML, not diff content, when fetched server-side — fixed via a confirmed `.diff`-suffix URL transform.
3. Reputation-ledger key-casing mismatch — an unnormalized internal write vs. a force-lowercased external read silently made every real address return the zeroed default. Fixed by normalizing at every write and read site.

**A fourth real bug, found only after live deployment to Vercel, not caught by any check available during the build itself:** `createAccount()` was called on the connected wallet's address, when that function actually expects a private key — confirmed against GenLayer's own SDK docs. This did not throw at compile time (both are hex strings) and could have silently produced broken signing on real write transactions. This is now documented in section 7 as a standing frontend rule. The build environment for this contract had no network access at all, meaning no real `npm install`/`tsc`/`vite build` ever ran until the person deploying it did so themselves on Vercel — this bug is the direct, confirmed proof that "passed every check available in a no-network sandbox" and "passed a real compiler" are different claims, not just a theoretical caveat.

**Not yet tested:** the `compliant` verdict branch with populated `resolution_hours` math has never been observed live, because every real advisory queried had `closed_at` unset — which the contract correctly reports as `unverifiable` rather than guessing. The arithmetic itself was verified correct by direct code inspection and an independent oracle cross-check (see section 4's Bug 8), not by live execution finding a real qualifying advisory.

**Known, deliberate gaps:** no response-time SLA variant (GHSA has no maintainer-response timestamp field at all, confirmed against GitHub's own REST API docs before the contract was written); the fix-substantiveness judgment can only reason about what GHSA's own record links to — a fix never referenced back into the public advisory is invisible to this contract; no deadline/expiry automation on unresolved compliance checks (mirrors Recourse's own accepted gap on the same pattern); `reasoning_summary` content validation remains a length threshold rather than full criteria-based validation — a smaller, less load-bearing gap here than in prior contracts, since the verdict, fix-substantiveness, and resolution-hours fields are all fully re-derived and independently compared; only the free-text summary explaining the verdict is length-checked.

**Portal outcome (updated Sep 2026): Accepted, 380 pts.** Two review rounds by a staff reviewer; the fixes (canonical repo binding, duplicate/invalid filing rejection, repo-backed ownership proof, challenge/finalize flow in the app) are described in section 15.

**Standing knowledge-transfer document:** this build produced `LESSONS.md` at its own repo root — a standalone document written specifically for a future session with no memory of this build, structured the same way this section's own bug catalog is structured (confirmed facts stated as rules, each with its evidence). Every fact in it that is durable and reusable across future builds, not specific to this one contract, has now been folded into this document's own sections 2, 4, 7, 8, and 9 above — `LESSONS.md` itself remains in the SentinelSLA repo as the dated, build-specific record of how each fact was found, not as a second copy of this document's own standing rules.

### Ledger of Record — reference implementation (dispute mechanics)
Two-sided dispute arbitration. Claimant stakes GEN + evidence URL; respondent rebuts with counter-evidence URL; run_nondet_unsafe leader/validator each independently fetch both parties' evidence and judge against a charter; settlement (slash/refund/protocol-pool split) happens strictly after the nondet call returns; one appeal per dispute, re-fetches evidence fresh, tighter confidence band on appeal. This is the reference for dispute/settlement mechanics and narrative; for the nondet code pattern itself, Copyleft (sections 4-6) is now the more complete and thoroughly-verified reference, since Ledger of Record predates the full bug catalog.
