## 2. Concept evaluation framework — run before writing any code

This is the gate a new idea must pass before you invest days into it. NEXUS, VERITY, and SourceChecker were all built without this filter and are now stuck borderline. Apply all four tests to any new concept:

**Test 1 — Consensus necessity (the most important test, and the one the July 2026 rejection category is built around).**
Ask: does this contract judge a *contested* claim where an adversarial party benefits from a false answer? Not "is there a question an LLM can answer" — a genuinely adversarial dispute.
- Passes: Ledger of Record (claimant vs respondent, each with incentive to lie or omit). Copyleft (claimant benefits from a false "violation" verdict, respondent from a false "compliant" one).
- Fails: NEXUS/VERITY/SourceChecker (single fetch, single judgment, no party benefits from the LLM being wrong — it's an oracle question, not a dispute).
- Rule of thumb: if you can't name *who benefits from a false verdict*, multi-validator consensus is decorative, not structural, and the project belongs off-chain.
- Directly confirmed in staff's own words (Discord, builder-announcements, Aug 2026): "GenLayer must solve a genuine trust problem, not just produce a better LLM response." Independent confirmation of this test from the team itself, stated as a Projects-track expectation, not just an inference from rejection patterns.

**Test 2 — Evidence verifiability.**
Can the claim be checked against a real, independently fetchable source (not just described by the submitter)? Is there more than one piece of evidence that could conflict (claimant's URL vs respondent's URL; two data sources that might disagree)? A single-source fetch is weaker than a two-sided or cross-referenced one.

**CONFIRMED REJECTION (SourceChecker, rejected Jun 25 2026):** staff's exact rejection reasoning was that a caller-selected page can only prove the page repeats a claim — it doesn't confirm the claim is true, just that some webpage says it. This is the precise, portal-confirmed failure mode of "evidence" that is (a) chosen entirely by whichever party is making the claim, and (b) not cross-checked against anything independent. The fix pattern that passed on Copyleft: keep the caller-selected/party-selected evidence legs, but add at least one fixed, non-optional, independently-authoritative evidence source that neither party controls (e.g. SPDX canonical license text) and require the verdict to be checked against that fixed source, not just against the parties' claims about each other. A contract where every evidence source is picked by a claimant/respondent is the SourceChecker failure pattern regardless of how many sources there are — the test is whether at least one leg is fixed and external, not the total count.

**Evidence must be structurally derived, never submitter-supplied, even when it's not the "main" claim (confirmed twice — SourceChecker Jun 2026, Chronomark Aug 2026, see section 11 for Chronomark's full entry).** SourceChecker's failure was a caller-selected evidence *page*. Chronomark's was structurally the same failure wearing different clothes: a submitter-supplied evidence *URL* with no binding to the task it was supposed to prove, plus a submitter-set deadline with no precommitment. Any field a contract fetches or compares against — evidence URL, target identifier, deadline — must be either (a) derived deterministically from other locked fields, never taken as raw submitter input, or (b) locked at a genuinely prior step, before the outcome could be known (e.g. a deadline set at creation, never at the same moment as the completion claim). A free-text field the submitter fully controls, feeding directly into what gets fetched or compared, is the single recurring defect across both rejections — check for this specifically on every new concept, not just "is there an independent fetch."

**Rule 0.8 — evidence-to-identifier binding, distinct from Rule 0.7 and from the paragraph above (confirmed live, CitationChain, Aug 2026 rejection).** The paragraph above is about *where the fetch target comes from* — deterministic derivation vs. raw submitter input. This rule is about a narrower, later question that a contract can still fail even after getting that part right: once a fetch genuinely goes to a deterministically-derived, independently-authoritative endpoint, does anything confirm the record that comes BACK actually corresponds to the specific identifier the caller named — or could the fetch succeed against a real, correctly-sourced record that simply belongs to something else? CitationChain's confirmed rejection wording: *"the fetched record and citation-list URLs are never verified to belong to the stored patent identifiers."* The contract fetched from a real structured API, deterministically, per Rule 0.7's own standard — and still failed, because nothing checked that the record's own identity fields echoed the claimed patent ID before that record was allowed to influence the verdict. **Check this explicitly on every new concept, as a distinct step from Rule 0.7:** after confirming the fetch target is deterministically derived, separately confirm that either (a) the fetched response contains a field genuinely identifying what it's a record OF, and the contract checks that field against the claimed identifier before use, or (b) the endpoint's own structure makes mismatch impossible (e.g. a REST path that 404s on any ID but the exact one queried, rather than returning a plausible unrelated record). This is not a rule to apply to every contract mechanically — it specifically matters for CROSS-REFERENCE and CITATION-style concepts, where a claim is "does A relate to B" rather than "is A true," since that's the shape where a real-but-wrong record can slip through the identifier check unnoticed. A concept whose evidence source can only ever return one canonical record for one canonical identifier (most single-entity attestations) doesn't need a separate check here — Rule 0.7's derivation requirement already closes the gap for those.

**A related but separate binding gap — standing/control claims (confirmed live, DomainClaim, Aug 2026, two rejections).** DomainClaim's first rejection: *"control_confirmed only matches public RDAP identity text and never proves the filer controls the domain."* This is neither Rule 0.7 nor Rule 0.8 — the evidence fetch was already deterministic (Rule 0.7 satisfied) and already correctly scoped to the claimed domain (Rule 0.8 satisfied, in spirit). The actual gap: some claims aren't "is this fact true" at all, but "does the caller specifically have STANDING or CONTROL over the thing being attested" — and identity text alone, however correctly fetched, can never establish that a specific caller (as opposed to anyone who can read the same public page) is the one with standing. **This needs a second, independent channel that only someone with genuine control could satisfy** — DomainClaim's fix derives a caller- and claim-specific token deterministically and requires it to appear in a DNS record only the domain's actual controller could publish, gating the strongest verdict value on that channel succeeding, never on LLM-judged text alone. Check for this specifically when a concept's claim is about ownership, operatorship, or control of something — not when it's about a fact concerning something. This is a narrow, mechanism-specific fix (DNS is not a general pattern; a different control claim would need a different independent channel), not a default every contract should carry. **Status note:** DomainClaim's fix for this exact gap was itself insufficient on a second review round (see section 11's DomainClaim entry) — the general principle (an independent, caller-specific channel is needed for standing/control claims) held up under review, but the specific implementation of the SECOND nondet round consuming that channel's result had its own separate defects. Treat the principle as confirmed; treat any specific implementation of it, including DomainClaim's own, as needing its own independent audit before reuse.

**Verdict-enum reachability (confirmed live, RetractionWatch, Aug 2026 rejection) — check independently of both rules above, on every concept with a multi-value verdict.** RetractionWatch's confirmed rejection: *"`sources_conflict` remains in the contract's verdict model even though it is unreachable."* The contract's own docstring had already disclosed this as a known, named limitation — disclosure did not satisfy the reviewer. **Before submitting any contract with an enumerated verdict/outcome type, trace every value in that enum against the actual `leader_fn` code path that could produce it.** A value that `validator_fn`'s membership check accepts as legal, but that no branch of `leader_fn` can structurally ever emit (because an earlier deterministic gate — e.g. "only one evidence source is ever fetched, depending on an identifier type fixed at registration" — makes reaching the branch that would produce it impossible), must be either (a) made genuinely reachable, or (b) deleted from the valid set entirely, before submitting. This is now a mandatory pre-submission check for both tracks (see section 9's checklists) — it is not the same failure as documentation not matching the build (existing rejection category, section 10); it is a live-code defect that happens to ALSO be honestly documented, which is not a defense.

**Test 3 — Novelty against your own tracker + the live portal.**
Check the tracker in section 11 first. Then search the portal for anything structurally similar (not just same industry — same *mechanism*). A new "X but for Y industry" isn't novel if the underlying consensus mechanism is identical to something already accepted.

**Genre and complexity rotation, applied alongside Test 3 (not a fifth test — a constraint on how Test 3 is satisfied):** the next concept must differ from the immediately preceding build in at least genre (the real-world domain — freelance work, licensing, trade, academic, etc.) or mechanism shape (adversarial two-party dispute vs. single-party attestation vs. reputation-based vs. staked). Two consecutive builds in the same genre with only the mechanism swapped, or the same mechanism with only the genre swapped, both fail this even if each would individually pass Test 3 against the full tracker. This exists specifically so builds stay varied by default rather than drifting toward whatever pattern was most recently proven working — Copyleft's evidence-arbitration shape being proven and well-documented is a reason to reach for something structurally different next, not a reason to reuse it again. Complexity is a separate axis from novelty: a simple, low-complexity concept that's genuinely different in genre or mechanism from the last build satisfies this fully — "different" does not mean "harder." For the Intelligent Contracts track specifically (section 10.1), favor smaller, single-technique concepts over ambitious multi-feature ones; the track exists for fast, focused technology demonstrations, not compressed Projects.

**Test 4 — Depth potential.**
Can this concept support a genuine appeal/dispute/escalation layer, multiple contract iterations, or a richer narrative arc — the kind of depth the "depth beats quantity" strategy shift rewards? A concept that's "done" after one write function and one view function is thin by construction, regardless of code quality.

**Depth potential is Projects-track guidance by default.** For the Intelligent Contracts track (section 10.1), Test 4 is optional, not required — a single-technique contract that's "done" after demonstrating one genuinely novel pattern is a complete, appropriate submission for that track specifically, not a thin one. Don't force appeal/escalation layers onto a Contracts-track submission to satisfy Test 4 if the concept doesn't naturally call for one; that's scope-creep away from the track's own stated purpose (section 10.1: "keep it small").

**Multi-entity concepts — build them out fully when the concept genuinely calls for it.** If a real-world concept has more than one distinct, structurally different tracked thing — not just claimant vs. respondent, but genuinely separate entities with their own lifecycles (e.g. a standing commitment locked once, separate from individual checks filed against it, separate from challenges filed against a specific check) — build that as multiple record types with the full rigor of section 4 applied to every one of them, rather than compressing a multi-part concept into one bloated record type to keep the file smaller. This cuts both ways: don't compress a concept that genuinely has several real moving parts, and don't add entities that aren't real just to appear more substantial. The test is always whether the concept itself has that many distinct moving parts — not a target entity count, and not a page-count target. A single well-executed entity remains a complete contract when the concept genuinely only has one real moving part.

**Audit a real, comparable contract before writing any code, whenever one is reachable.** Before starting a new concept, if a structurally similar contract exists anywhere accessible — a live portal submission, an open-source example, a competing project — read its actual source, not just its README or its score. This has repeatedly been the single highest-leverage step available before a build starts: it is what surfaces real validator-rigor gaps in a comparable design before repeating them, and it is what surfaces genuinely new GenVM API options (e.g. `gl.eq_principle.prompt_comparative` and `gl.evm.contract_interface`, both real, current, documented alternatives to the `run_nondet_unsafe`/`get_contract_at` patterns this document treats as canonical — worth knowing exist even when the hand-written `run_nondet_unsafe` pattern remains the safer default for anything where every decision-bearing field needs independent re-derivation, since `prompt_comparative`'s equivalence-principle string can be written to exclude fields from agreement without that being obvious from the contract's surface). Do this before assuming a concept is technically novel enough not to need it — novelty of concept and novelty of technical pattern are different questions, and only a real source-level audit answers the second one.

**Score guide:** a concept needs to clearly pass Test 1 to be worth building at all. Tests 2-4 determine how strong an acceptance it can realistically get under current review standards — see section 10's benchmark discussion, which is now calibrated against the current three-submission set (Copyleft 200 pts, Recourse 200 pts, Chronomark rejected) rather than the now-stale Questera 760pt/Sigil 320pt reference points from before the stricter standard took effect.
